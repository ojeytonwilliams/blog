## A slight change of pace

I have occasion to learn a bit of Rust for work purposes, so I figured I should get some grounding in the basics rather than blindly assume I know what I'm doing.

It's been quite a pleasant surprise so far.  It feels like they've taken on board a lot of ideas I really like from other languages. Notably Haskell feels like a strong influence. Is it strong? Wikipedia lists it as an influence along with 20 (!) others, so it could be, but I don't have time to dig into the history right now.

So, what's this post about? I just wanted to talk a little about a couple of features that were a little surprising to find in Rust: shadowing and continuing out of matches. That and some brief digressions into some silly mistakes I keep making.

## Shadowwhating

If you declare a variable in Rust, you're free to re-declare it.  Not so in a variety of other languages, including Haskell:

```hs
seven = 7
seven = 8 -- Not allowed!  
```

whereas in Rust

```rust
fn main() {
  let seven = 7;
  let seven = 8; // Absolutely fine!
}
```

It's intriguing that two languages that both prize correctness could end up with opposite approaches to this feature. So, what gives?

## Shadowwhying

As I see it, disallowing shadowing makes sense from the perspectives of functional language design and simplicity. Why simplicity? Well, it's trivially simpler in that there's one fewer thing you can do in the language!  Why functional?  Well, shadowing is remarkably similar to mutation in practice.  You had something, `seven`, that was one thing, `7`, and you changed it - it's `8` now.

On the other hand, allowing shadowing makes sense from a practical perspective. It's a very common pattern to have data in one form that you want to transform into another form for later use.  If you can't shadow, then the most natural solutions are either mutations or intermediate variables.  For example, in JavaScript, you can't write

```js
let five = "5";
let five = parseInt(five);
```

because you're not allowed to re-declare (shadow) variables you define with `let`. However both

```js
let five = "5";
five = parseInt(five);
```

and

```js
const fiveStr = "5";
const five = parseInt(fiveStr);  
```

are valid.  But there are problems with both.  The mutation approach leaves `five` free for further mutation.  There's no way to signal that mutating `five` isn't desirable. The intermediate variable approach is ugly, cluttered and forces you invent multiple names for what is more or less the same thing.

Rust's approach solves this elegantly.  You're allowed to shadow because it's convenient (no intermediate variables), but you can signal that the variable should not be changed (it's still immutable).  Anyone reading your code can see your intention and the compiler will shout at them if they do something silly.

## Continue! 

One of my favourite features of Haskell is pattern matching.  `case` is awesome:

```hs
stringifyMaybe :: Maybe String -> String
stringifyMaybe maybe = case maybe of
  Just str -> str
  Nothing -> "Nothing to see here"
```

Not that you need to create `stringifyMaybe` since `fromMaybe` exists, but it illustrates how elegant pattern matching can be.

Rust supports something very similar with the `match` keyword

```rust
fn stringify_option(opt: Option<&str>) -> &str {
    match opt {
        Some(str) => str,
        None => "None to see here",
    }
}
```

Almost identical.

However, even though Rust takes a lot of ideas from functional languages, it is very definitely not a functional language.  That shows up in the fact it allows you to `break` or `continue` out of a `match`.

Here's an example from the Rust Book (the Brown [version](https://rust-book.cs.brown.edu/ch02-00-guessing-game-tutorial.html#handling-invalid-input)):

```rust
let guess: u32 = match guess.trim().parse() {
    Ok(num) => num,
    Err(_) => continue,
};
```

pretty nice code, but not functional. If a language is strictly functional, it should provide "referential transparency". This means that you should be able to replace an expression with whatever it evaluates to. If that replacement does not affect the behaviour of the program, then it is referentially transparent.  As a trivial example `let five = 2 + 3` demonstrates this because you could replace `2 + 3` with `5` and nothing would change (aside from, perhaps, a minuscule change in the performance).  If you use `break` or `continue` this is no longer the case, since there simply isn't a `u32` value that's equivalent to "stop evaluating the loop here and go back to the start of it".  How could there be?

Is this a problem? Probably not. Rust isn't forcing you to use these control structures - they're just there if you need them.

## A semi-colonic gotcha

Rust doesn't rely on `return` to return values. A little bit like Haskell, the default assumption is that something is an expression and therefore you're interested in the value of said expression.  Consider this

```rust
fn five() -> i32 {
  5
  // there's no need to use the return below
  // return 5;
}
```

however

```rust
fn five() -> i32 {
  5;
}
```

does not compile since the return type, `()` or 'unit', does not match the declared return type `i32`. Why is it unit? Because the semi-colon swallowed the expression, turning it into a statement.

### Brief digression on declarations

Something I rather like about Rust is that you _have_ to declare functions completely, including the return type.  It makes silly mistakes like missing a `;` trivial to find and fix.  Haskell's approach is also quite nice, as long as you take warnings seriously (i.e. make use of `-Werror` to upgrade warnings to errors).  The warning about a lack of declaration is helpful and the language server can fix it for you.

In practice Rust and Haskell's approaches are basically the same. Rust is just a little stricter.

Anyways, I'll leave this section with one exception. You don't have to provide the `unit` return type if that's what your function does.  So, it's not technically true that you always have to be completely explicit with your declarations!

### What gotcha?

It's only a small one, to be honest, but

```rust
fn gotchish() {
  let y = {
    let x = 1;
    x + 2;
  }

  println!("y: {y}");
}  
```

doesn't work how you might expect.  Thankfully it doesn't work at all (which is why it's not much of a gotcha); instead it fails to compile with a (mildly) confusing error.  The compiler tells you that it doesn't know how to format `y` since `y` has type `()`. As previously mentioned `;` swallows return types, which is obviously not what the code was supposed to do.

The takeaway is that unlike, say, JavaScript, semi-colons are not largely decorative, they matter.

## Reference to what

The [penultimate quiz](https://rust-book.cs.brown.edu/ch04-02-references-and-borrowing.html) in the section on references and borrowing is a good one, particularly the last question.

Here's the code

```rust
fn main() {
    let v1 = vec![1, 2, 3];
    let mut v2 = v1;
    v2.push(4);
    println!("{}", v1[0]);    
}  
```

and they give four answers (all correct descriptions of how the program would behave if it could be compiled).

1. v1[0] reads v1, which points to deallocated memory
1. v1 has been moved into v2 on line 2
1. v1 has its pointer invalidated by the push on line 3
1. v2 owns the vector data on the heap, while v1 does not

The question is "Which of the following best describes the point at which undefined behaviour occurs in this program?" and the answer is 1.  That's because all the others, while true, do not directly cause undefined behaviour.

This tripped me up for a while because I had misunderstood what actually happens to a variable once it's aliased (`let mut v2 = v1;` in this case). I thought that meant `v1` was essentially gone. If so, how could it point to deallocated memory?  Simply put, it's not gone. It lives until the main frame is disposed of, so it is still a pointer and it still points to something.  The problem, as the correct answer states, is that the memory that `v1` points to gets deallocated as part of the push, `vs.push(4)`. In general memory *might* get deallocated, it depends on the vector's length and capacity, so it makes sense for the borrow checker to play it safe here.

## Mild shock (format string edition)

I only mention this because I keep doing it! Doing what? Writing format strings wrong:

```rust
fn main() {
  let num = 1;
  println!("Number: { num }") // oops
}  
```

which isn't valid.  It's trivial really, but format strings have a very string syntax: if you want to insert a variable into them, you must not have whitespace around the variable.

```rust
fn main() {
  let num = 1;
  println!("Number: {num} ") // no oops
}  
```

I suspect JavaScript has poisoned my mind.
